## 系统设计基础

_系统设计是指如何构建能够在大规模环境中稳定运行的软件。本文件涵盖了客户端-服务器架构、网络协议、DNS、代理、负载均衡、缓存、数据库、消息队列、一致性模型以及弹性设计模式等内容。_

- 所有投入实际使用的机器学习系统都是分布式系统。推荐引擎并非仅仅是一个模型——它实际上还包括API服务器、特征存储系统、模型注册表、缓存层、消息队列以及监控组件，所有这些组件都通过网络相互连接。理解系统设计才是区分“我训练出了一个模型”与“我打造出了一个产品”的关键。

- 杰出科技企业（谷歌、Meta、亚马逊、OpenAI）在招聘时都会考察候选人的系统设计能力。本章为你提供了相关的基础知识（即本文件）、云基础设施相关内容（文件02）、扩展策略（文件03）、针对机器学习场景的设计方法（文件04），以及实际案例分析（文件05）。

## 客户端-服务器架构

- 基本工作模式为：**客户端**发送请求，**服务器**处理该请求并返回响应。你的浏览器作为客户端，会向google.com这个服务器发送HTTP请求，而服务器则会返回HTML内容。

- **请求-响应模型**为同步式：客户端需要等待响应。虽然简单，但存在瓶颈——客户端在等待期间处于空闲状态，同时服务器也必须先处理完当前请求才能继续处理其他请求。

- **无状态服务器**不会记住之前的请求信息。每个请求都包含处理该请求所需的所有数据。这样一来，系统的扩展就变得很简单：任何服务器都可以处理任意请求，因此可以在负载均衡器后添加更多服务器来提升处理能力。

- **有状态服务器**会在不同请求之间保留状态信息（比如用户会话信息）。这类服务器的扩展较为困难，因为来自同一用户的请求必须被发送到同一个服务器上。现代系统通常会将状态信息存储在数据库或缓存中（如Redis），从而避免使用有状态服务器。

## 网络协议

- 第13章已经介绍了网络相关知识（TCP/IP协议层、套接字）。这里则重点介绍系统设计中常用的应用层协议：

- **HTTP/HTTPS**：网页及大多数API所使用的协议。常见的请求方法包括GET（读取数据）、POST（创建/预测数据）、PUT（更新数据）、DELETE（删除数据）。HTTPS则通过TLS加密技术来保障数据安全（详见第13章的安全相关内容）。REST API（见第15章文件03）就是基于HTTP构建的。

- **WebSockets**：能够在客户端与服务器之间建立持久的双向连接。与HTTP那种“请求→响应→连接关闭”的模式不同，WebSockets能够保持连接畅通，从而实现实时数据传输。它被广泛应用于大语言模型令牌的实时传输、实时仪表板以及聊天应用等领域。

- **gRPC**：谷歌开发的RPC框架。它基于HTTP/2协议，并使用Protocol Buffers进行数据序列化处理——这种二进制格式的体积比JSON小约10倍，传输速度也更快。gRPC支持双向、服务器端及客户端端的流式数据传输。在那些对性能要求较高的内部服务间通信场景中，人们会使用gRPC。Triton Inference Server（见第15章）和TensorFlow Serving也都采用了gRPC技术。

- **Protocol Buffers**：通过`.proto`文件来定义消息结构。

```protobuf
message PredictRequest {
    repeated float features = 1;
    string model_version = 2;
}

message PredictResponse {
    float prediction = 1;
    float confidence = 2;
}

service ModelService {
    rpc Predict(PredictRequest) returns (PredictResponse);
}
```

- 该架构会被编译为各种语言的客户端和服务器代码（Python、C++、Go、Java）。类型安全、向后兼容性以及高性能都是自然而然具备的。

## DNS

- **DNS**（域名系统）负责将人类可读的域名转换为IP地址（详见第13章）。在系统设计中，DNS还能实现以下功能：

- **通过DNS实现负载均衡**：为同一个域名返回不同的IP地址，从而将流量分配到多台服务器上。这种方法简单，但粒度较粗（DNS查询结果会被缓存数分钟到数小时，因此流量无法快速重新分配）。

- **基于地理位置的路由**：根据客户端的所在位置，返回距离最近的数据中心的IP地址。位于东京的用户会连接到日本的数据中心，而位于伦敦的用户则连接到欧洲的数据中心。

- **故障转移**：当某台服务器出现故障时，DNS就会停止返回该服务器的IP地址，新的客户端会自动连接到正常的服务器上。但由于有缓存的存在，部分客户端仍会在几分钟内继续尝试连接已故障的服务器（这就是TTL问题的体现）。

## 代理

- **代理**是位于客户端与服务器之间的中间节点：

- **反向代理**（位于服务器前端）：客户端首先连接到代理，再由代理将请求转发给后端服务器。客户端并不知道是哪台服务器处理了该请求。**Nginx**和**HAProxy**是常见的反向代理软件，它们具备负载均衡、SSL解密、缓存、限流以及数据压缩等功能。

- **API网关**：专为API设计的反向代理。它负责处理身份验证、限流、请求路由（不同的路径对应不同的服务），以及API版本管理。**Kong**、**AWS API Gateway**和**Envoy**都是常用的选择。

- 在机器学习应用中，API网关会部署在模型服务器之前。它负责验证API密钥、对免费用户实施限流、将/v1/predict类型的请求路由到模型服务器A，将/v2/predict类型的请求路由到模型服务器B，同时还会收集使用统计信息。

## 负载均衡

- 当拥有多台服务器时，**负载均衡器**的作用就是将传入的请求均匀分配到这些服务器上。

![负载均衡器将请求分配到多台后端服务器上](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/load_balancer.svg)

- **常用算法**：
- **轮询法**：按顺序将请求发送到各服务器（1、2、3，然后又是1、2、3……）。这种方法简单且公平，但无法考虑服务器的实际负载情况。
- **最少连接数法**：将请求发送到当前活跃连接数最少的服务器。对于处理时间不固定的请求来说，这种算法更为合适（有些LLM请求只需要处理10个token，而有些则需要处理1000个token）。
- **加权轮询法**：容量较大的服务器会收到更多的请求。例如，拥有80GB GPU内存的服务器，其处理请求的能力是拥有40GB内存的服务器的两倍。
- **一致性哈希法**：通过对请求键进行哈希处理，将请求定向到特定的服务器。相同的请求键总是会被发送到同一台服务器。这种方法适用于缓存、会话保持以及前缀缓存等场景（详见第17章：具有相同系统提示词的请求会被发送到存储有相应KV缓存的服务器上）。

- **L4层负载均衡与L7层负载均衡的区别**：
- **L4层**（传输层）：根据IP地址和端口来路由请求。速度快，但无法查看请求的内容。
- **L7层**（应用层）：根据HTTP路径、头部信息或请求体内容来路由请求。可以将/api/chat类型的请求路由到聊天服务器，将/api/embed类型的请求路由到嵌入服务服务器。虽然速度稍慢，但灵活性更高。

## 缓存

- **缓存**的功能是将频繁访问的数据存储在高速存储介质（如RAM）中，从而避免重复计算或重复获取这些数据。

![缓存策略：先检查缓存，若未找到则从数据库获取并存储到缓存中以供下次使用](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/cache_aside_pattern.svg)

- **常见的缓存策略**：
- **缓存旁路策略**（延迟加载）：应用程序首先检查缓存。如果缓存中没有所需数据，则从数据库获取数据，将其存储到缓存中后再返回给客户端。这是最常用的缓存策略。
- **直写策略**：每次写入操作都会同时被记录到缓存和数据库中。这样可以确保缓存始终处于最新状态，但会增加写入操作的延迟。
- **回写策略**：写入操作仅被记录到缓存中，缓存会异步地将数据刷新到数据库中。这种方式的写入速度最快，但如果缓存在数据刷新之前发生故障，就有可能导致数据丢失。

- **缓存淘汰策略**（当缓存已满时）：
- **最近最少使用策略**：淘汰那些最长时间未被访问的数据。这是最常用的淘汰策略。
- **最少使用频率策略**：淘汰那些被访问频率最低的数据。当某些数据一直被频繁访问时，这种策略更为适用。
- **生存时间策略**：数据在经过指定时间后会自动过期。这种策略适用于那些会过时的数据（例如，模型预测结果可以缓存5分钟，特征值则可以缓存1小时）。

- **CDN**（内容分发网络）：是一种用于存储静态内容（如图片、JavaScript文件、CSS文件）的全球分布式缓存系统。全球范围内有100多个位置的服务器，它们会从距离用户最近的服务器提供缓存内容。在机器学习应用中，模型权重也可以存储在CDN上，从而实现快速下载。

- **Redis**：是目前最常用的内存缓存/数据库工具。它支持字符串、列表、集合、有序集合、哈希表以及流等多种数据结构。其响应时间可达到亚毫秒级别。Redis常被用于缓存模型预测结果、存储会话数据、实施限流（统计每分钟每个用户的请求次数），以及实现实时特征服务。

- 在机器学习应用中，可以对重复出现的输入数据进行预测结果缓存。如果有很多用户询问“法国的首都是哪里？”，只需计算一次答案，之后就可以直接返回缓存中的结果。在聊天机器人系统中，缓存命中率通常在20%到40%之间，这有助于降低GPU的使用成本。

## 数据库

### SQL数据库（关系型数据库）

- **SQL数据库**（如PostgreSQL、MySQL）将数据存储在由行和列构成的表格中。表格之间的关系通过外键来表示。查询操作则通过SQL语句来完成。**ACID特性**能够确保数据的可靠性：

- **原子性**：一个事务要么完全执行完成，要么完全回滚，不会存在部分更新的的情况。
- **一致性**：数据库的状态会从一种有效的状态转变为另一种有效的状态。所有的约束条件（如唯一键、外键约束）都会得到满足。
- **隔离性**：多个并发事务之间不会相互干扰。
- **持久性**：一旦数据被提交，即使系统发生崩溃，这些数据也会被保存下来（因为数据会在确认之前被写入磁盘）。
- SQL数据库的优势在于：能够处理具有关联关系的结构化数据、复杂的查询操作（连接、聚合等），同时还能满足严格的一致性要求以及数据完整性需求。

### NoSQL

- **NoSQL数据库**为了实现更高的可扩展性和灵活性，放弃了部分ACID特性：

- **键值存储**（Redis、DynamoDB）：结构最为简单，可通过键快速检索数据。常用于缓存、会话存储以及特征存储。
- **文档存储**（MongoDB、Firestore）：以类似JSON的格式存储数据，架构灵活（每份文档可以包含不同的字段）。适用于存储用户资料、产品目录以及配置信息。
- **列族存储**（Cassandra、HBase）：专为高写入量及时间序列数据而设计。常用于事件日志记录、指标统计以及数据分析。
- **图数据库**（Neo4j）：用于存储节点和边关系，擅长处理路径查询。常被用于社交网络、知识图谱以及推荐系统。
- **向量数据库**（Pinecone、Milvus、Weaviate、FAISS）：用于存储高维向量数据，并支持近似最近邻搜索。对于语义搜索、RAG技术以及推荐系统而言非常重要。

### CAP定理

- 在分布式数据库中，这三项属性中最多只能同时具备两项：

- **一致性**：每次读取都能得到最新的数据。
- **可用性**：无论某些节点是否出现故障，所有请求都能得到响应。
- **分区容错性**：即使网络出现分区，系统仍能继续运行。

![CAP定理：由于网络分区是不可避免的，因此需要在这两者之间做出选择——要么选择一致性，要么选择可用性](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/cap_theorem.svg)

- 由于在分布式系统中网络分区是不可避免的，实际的选择就是**CP模式**（保持一致性，但在分区期间可能无法提供服务——例如PostgreSQL）与**AP模式**（保证可用性，但在分区期间可能会返回过时数据——例如Cassandra、DynamoDB）。

- 对于机器学习应用来说，特征存储通常选择AP模式（稍有过时的特征值总比没有预测结果要好）；而模型注册系统则选择CP模式（使用错误的模型版本会导致严重后果）。

### 分片

- **分片**是将数据库的数据分散到多台机器上存储，每片只保存部分数据。

- **哈希分片**：通过哈希函数来确定数据应存储在哪片上。计算公式为：`shard = hash(user_id) % num_shards`。这种方式能使数据分布均匀，但无法进行范围查询。

- **范围分片**：每片负责存储一定范围内的数据（例如，第1片存储A到G的用户数据，第2片存储H到N的用户数据）。这种方式支持范围查询，但也可能导致某些数据被频繁访问（比如有很多用户的名字以“S”开头）。

- **重新分片的问题**：添加新的分片后会打破原有的哈希映射关系。**一致性哈希**技术可以最小化数据迁移量：在添加第n个分片时，只需移动大约1/n的键值对即可。

### 数据库索引

- **索引**是一种数据结构，它能够加快查询速度，但代价是会增加存储空间并降低写入速度。如果没有索引，查询时需要遍历所有行（时间复杂度为O(n)）；而有了索引后，查询速度可提升到O(log n)。

- **B树索引**（默认索引类型）：是一种平衡树结构（详见第13章和第14章），每个节点包含多个键值以及对其他节点的引用。B树非常适合缓存使用（因为其节点宽度适合放入缓存中），并且支持范围查询（如`WHERE age BETWEEN 20 AND 30`）。大多数SQL数据库都使用B树作为索引结构。

- **哈希索引**：通过哈希函数将键值映射到对应的数据行位置。查询速度为O(1)，但不支持范围查询。适用于精确匹配查询（如`WHERE id = 12345`）。

- **复合索引**：是对多个列创建的索引。例如`CREATE INDEX ON users(country, city)`，这样的索引可以加快按国家或国家加城市条件进行查询的速度，但无法单独按城市进行查询（查询条件中必须包含最左边的列）。

- **权衡取舍**：虽然索引能加快读取速度，但会降低写入速度（因为每次插入、更新或删除数据时都需要更新索引），同时还会占用一定的存储空间（每个索引大约占表大小的10%-30%）。因此不必为所有列都创建索引，只需为那些经常被查询的列创建索引即可。

- **对于机器学习系统而言**，特征存储的在线数据库需要为实体键（如user_id、item_id）创建索引，以便快速查找特征数据；而实验跟踪数据库则需要为（experiment_id, metric_name）这对字段创建索引，以便在控制台中查看实验数据。

### API设计

- 系统之间通过API进行通信。良好的API设计能让系统更易于使用、更易于扩展，也便于调试。

- **REST规范**：用名词来表示资源路径（如 `/users`、`/models`），用HTTP方法来表示操作类型（GET表示读取，POST表示创建，PUT表示更新，DELETE表示删除），用状态码来表示操作结果（200表示成功，201表示创建成功，400表示请求有误，404表示找不到对应数据，429表示请求频率过高，500表示服务器错误）。

- **分页处理**：对于那些返回列表数据的接口，不应一次性返回所有数据。可以使用基于游标的分页方式（如`GET /items?cursor=abc&limit=50`），或者基于偏移量的分页方式（如`GET /items?offset=100&limit=50`）。对于大型数据集来说，基于游标的分页效率更高（因为基于偏移量的分页需要跳过大量数据行）。

- **版本控制**：在API路径前加上版本号，如`/v1/predict`、`/v2/predict`。这样就可以在不影响现有客户端的情况下对API进行升级。客户端可以自行决定何时升级到新版本；旧版本虽然已过时，但只要仍有流量使用，就不会被立即移除。

- **错误响应**：应返回结构化的错误信息，以便于调试。

```json
{
  "error": {
    "code": "INVALID_INPUT",
    "message": "Feature 'user_age' must be a positive integer",
    "details": { "field": "user_age", "value": -5 }
  }
}
```

## 消息队列

- **消息队列**将数据生成方（负责创建任务的服务）与数据处理方（负责处理这些任务的服务）解耦开来。数据生成方将消息发送到队列中，而数据处理方则在准备好时再取出这些消息。

- **为什么需要队列**：如果没有队列，一旦数据处理方处理速度较慢或出现故障，数据生成方就会被阻塞。而有了队列之后，数据生成方只需将消息发送出去即可，无需再操心后续处理；队列会暂时存储这些消息，直到数据处理方能够处理它们。

- **Apache Kafka**：这是一种分布式、持久化且具有高吞吐量的消息队列。消息被存储在“主题”中，每个主题又会被划分到多个节点上。数据处理方从各个分区中读取消息，并记录自己的读取位置（即“偏移量”）。Kafka能够确保同一分区内的消息按顺序处理，同时还能重新播放这些消息（因为其日志是持久化的）。

- **发布/订阅模式**：发布方将消息发送到某个主题，该主题的所有订阅方都会收到这份消息的副本。这种模式常用于事件驱动架构中——比如“有新模型被部署”这一事件，可以同时触发监控服务、A/B测试服务以及日志记录服务。

- 在机器学习应用中，预测请求通过HTTP方式发送过来，随后被放入Kafka队列中，由GPU处理单元进行处理，最终结果则通过回调或WebSocket方式返回。队列可以缓冲大量的请求，从而避免因GPU处理单元故障而导致请求丢失。

## 一致性模型

在分布式系统中，不同的节点可能对数据的理解有所不同。**一致性模型**则规定了系统应提供何种一致性保障：

- **强一致性**：一旦数据被写入，所有后续的读取操作（无论来自哪个节点）都会看到最新的数据值。这种模型易于理解，但处理速度较慢（因为需要节点之间进行协调）。

- **最终一致性**：数据写入后，一段时间内读取到的可能是过时的数据，但最终会显示最新值。这种模型处理速度快（无需节点间协调），但应用程序需要自行处理那些过时的数据。

- **因果一致性**：如果操作A在时间上先于操作B发生（例如先写入X，然后再读取X），那么系统会确保操作B能看到操作A的结果。不过，彼此无关的操作则可能以任意顺序被执行。

- **读自己写入的数据**：用户始终能够立即看到自己刚刚写入的数据，即便其他用户看到的还是过时的数据。这是大多数应用程序所要求的最低一致性水平。

## 高可用性策略

- **速率限制**：限制每个用户在特定时间窗口内可以发送的请求数量。这样可以防止滥用行为，确保公平访问。这一功能可以通过Redis中的令牌桶算法或滑动窗口计数器来实现。

- **断路器机制**：如果下游服务开始出现故障（错误率超过阈值），断路器就会“打开”，停止向该服务发送请求（并立即返回备用响应）。经过一段时间后，断路器会“半打开”，并发送测试请求。如果测试成功，断路器就会恢复正常工作。这种机制可以避免级联故障：比如当特征存储服务出现故障时，模型服务器仍可以返回预测结果，而不会因为每次请求都超时而无法工作。

- **背压机制**：当系统负载过重时，它会向上游发送信号，要求对方降低请求速度。系统不会接受过多的请求并导致故障，而是会提前拒绝这些多余的请求（通过429或503状态码）。客户端则会以指数退避的方式重新尝试发送请求。

- **带指数退避的重试机制**：如果某次请求失败，先等待1秒后再尝试；如果仍然失败，则等待2秒，然后是4秒、8秒，以此类推。此外，还可以加入随机延迟，以避免所有客户端同时重试（即“群体性重试”问题）。

- **幂等性**：如果重复执行某项操作，其效果与只执行一次相同，那么这项操作就是幂等的。例如，`PUT /user/123` 配合 `"name": "Alice"` 的请求体就是幂等操作（将名称设置为“Alice”两次也没问题）。而`POST /payments`则不是幂等操作（支付两次会导致问题）。确保操作具有幂等性，就可以让重试操作更加安全。

## 云计算

云计算为机器学习工作负载提供按需基础设施，无需自行购置硬件。本文涵盖了服务模型、主要云服务提供商、容器与Kubernetes、存储、云网络、无服务器计算、成本管理以及基础设施即代码等内容。

训练前沿模型需要数千个GPU连续运行数月时间。没有哪家初创公司能拥有如此规模的硬件。云计算允许你按小时租用这些资源：训练时扩大规模，推理时缩小规模，且仅需为实际使用的部分付费。对于在笔记本电脑之外构建机器学习系统的人员而言，了解云计算基础设施至关重要。

## 云服务模型

![云服务层级：IaaS赋予用户最大控制权，SaaS则最少](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/cloud_service_layers.svg)

云服务根据提供商的管理程度分为不同层级：

| 模型 | 用户管理的内容 | 提供商管理的内容 | 示例 |
| ------- || -------------- || ----------------- || ------ ||
| **IaaS**（基础设施） | 操作系统、运行时、应用程序 | 硬件、虚拟化、网络 | AWS EC2、GCP Compute Engine |
| **PaaS**（平台） | 应用程序、数据 | 操作系统、运行时、扩展、补丁更新 | AWS SageMaker、GCP Vertex AI |
| **SaaS**（软件） | 无需管理（直接使用即可） | 全部内容 | OpenAI API、Weights & Biases |
| **FaaS**（函数） | 单个函数 | 其余所有内容 | AWS Lambda、GCP Cloud Functions |

对于机器学习而言，大多数团队会混合使用这些模型：利用IaaS进行自定义训练（可完全控制GPU实例），借助PaaS实现托管训练和部署（SageMaker、Vertex AI负责协调工作），并使用SaaS工具（如W&B用于实验跟踪，OpenAI API用于基准对比）。

## 主要云服务提供商

### AWS（亚马逊云服务）

AWS是最大的云服务提供商（约占32%的市场份额）。其主要机器学习服务包括：

- **S3**：对象存储。用于存储数据集和模型权重的标准选择。容量几乎无限，价格约为0.023美元/GB/月。
- **SageMaker**：托管的机器学习平台。负责训练、超参数调优、部署及监控。
- **EKS**：托管的Kubernetes服务。
- **Lambda**：无服务器函数。虽不适合GPU工作负载，但可用于预处理和流程编排。

### GCP（谷歌云平台）

谷歌的云平台约占11%的市场份额。其主要机器学习服务包括：

- **Compute Engine**：虚拟机。提供搭载A100、H100的GPU实例，以及用于访问TPU的TPU VM。
- **GCS**：对象存储（类似于S3）。
- **Vertex AI**：托管的机器学习平台。原生支持JAX/TPU。
- **GKE**：托管的Kubernetes服务（由于谷歌是Kubernetes的创建者，因此该服务最为成熟）。
- **Cloud TPU**：GCP独有的产品，v5e和v5p版本适用于大规模训练。

### Azure（微软云）

微软云约占23%的市场份额。其主要机器学习服务包括：

- **Azure VM**：搭载A100、H100的GPU实例。
- **Azure Blob Storage**：对象存储。
- **Azure ML**：托管的机器学习平台。
- **AKS**：托管的Kubernetes服务。
- **OpenAI Service**：通过Azure API独家提供对OpenAI模型的访问权限。

## 容器与Kubernetes

我们在第13章（操作系统）中介绍了容器（Docker）和Kubernetes的概念，在第15章（部署）中讲解了其实际应用。此处我们将重点探讨**特定于云**的使用模式：

### 用于机器学习的Kubernetes

**Kubernetes（K8s）**能够大规模协调容器。关键概念如下：

- **Pod**：最小的可部署单元。包含一个或多个共享网络和存储的容器。一个模型服务Pod可能包含：模型服务器容器 + 用于收集指标的sidecar容器。
- **Deployment**：用于管理一组相同的Pod。它指定所需的副本数量；若某个Pod崩溃，K8s会自动创建替代副本。
- **Service**：为一组Pod提供的稳定网络端点。客户端连接到该服务后，K8s会将请求路由到健康的Pod。类型包括：ClusterIP（内部使用）、NodePort（通过节点端口对外提供访问）、LoadBalancer（通过云负载均衡器对外提供访问）。
- **StatefulSet**：类似于Deployment，但适用于有状态的工作负载。每个Pod拥有持久的身份标识和稳定的存储。常用于数据库和分布式训练场景（各工作节点需要稳定的身份标识以便通信）。
- **DaemonSet**：在每个节点上运行一个Pod。常用于：监控代理（如Prometheus node exporter）、日志收集器（如Fluentd）、GPU设备插件（如NVIDIA设备插件）。

- **K8s中的GPU调度**：NVIDIA设备插件会将GPU作为K8s资源暴露出来。Pod通过请求来使用GPU：

```yaml
resources:
  limits:
    nvidia.com/gpu: 2 # this pod needs 2 GPUs
```

- K8s将Pod调度到拥有2个可用GPU的节点上。这就是云ML平台为训练和推理分配GPU的方式。

### 自动扩缩容

- **水平 Pod 自动扩缩容器（HPA）**：根据指标（CPU使用率、请求速率、自定义指标如GPU利用率或队列深度）来调整Pod数量。
- **集群自动扩缩容器**：调整节点数量。如果因节点不足而无法调度Pod，集群自动扩缩容器会从云提供商处 provision 新的虚拟机。当节点利用率较低时，它会排空并终止这些节点。
- **KEDA**（Kubernetes事件驱动型自动扩缩容）：基于外部事件源进行扩缩容（如Kafka队列深度、HTTP请求速率）。它非常适合推理场景：当请求队列增长时扩容模型服务器，队列为空时则缩容。

## 存储

| 类型 | 特点 | 使用场景 | 示例 |
| ------ || ------ || ---------- || ------ ||
| **块存储** | 低延迟，绑定于单个虚拟机 | 操作系统磁盘、数据库 | AWS EBS、GCP持久磁盘 |
| **对象存储** | 容量无限，支持HTTP访问 | 数据集、模型权重、日志 | AWS S3、GCS、Azure Blob |
| **文件存储** | 可在多台虚拟机间共享，符合POSIX标准 | 共享训练数据 | AWS EFS、GCP Filestore、NFS |
| **数据湖** | 读时模式，存储原始数据 | 数据分析、特征工程 | Delta Lake、Iceberg、Hudi |

- **对于ML训练**：数据集存储在对象存储（S3/GCS）中。训练脚本从对象存储读取数据并载入内存。为了实现快速随机访问（如打乱后的数据加载），可采用以下方式：(1) 在训练前将数据集下载到本地SSD；(2) 使用高吞吐量的文件系统（如Lustre、FSx）；(3) 使用能够高效流式传输和缓存的数据加载库（如WebDataset、FFCV）。
- **模型权重**：存储在支持版本控制的对象存储中。一个70B参数的FP16模型大小约为140 GB。以1 GB/s的速度从S3加载需要约2.5分钟。将其缓存到本地SSD可缩短推理时的冷启动时间。

## 云网络

- **VPC**（虚拟私有云）：云环境中的隔离网络。虚拟机、数据库和服务均在VPC内通信。外部流量通过负载均衡器或网关进入。
- **子网**：将VPC划分为不同段。公有子网可访问互联网（用于API服务器）；私有子网则不能（用于数据库、GPU工作节点）。这相当于网络安全中的最小权限原则。
- **安全组**（AWS）/ **防火墙规则**（GCP）：用于控制允许的流量。“允许来自任意地点的端口80上的HTTP入站请求；仅允许来自我的IP的端口22上的SSH入站请求；阻止所有其他流量。”配置不当的安全组是云安全事故的首要原因。
- **服务网格**（Istio、Envoy）：管理K8s内的服务间通信。提供：mTLS加密（每个服务间调用均被加密）、流量路由（A/B测试：将10%的流量导向新模型）、重试机制、超时设置、熔断机制以及可观测性（记录哪个服务调用了哪个服务、耗时多久）。

## 无服务器计算

- **无服务器计算**（AWS Lambda、GCP Cloud Functions）：上传函数后，云提供商会在触发时运行它。无需管理服务器，也无需配置扩缩容。按调用次数付费（通常每百万次调用0.20美元加上计算时间费用）。
- **冷启动**：长时间未使用后首次调用会耗时更长（提供商需分配容器并加载代码）。冷启动时间为0.5–5秒，因此无服务器计算不适合对延迟敏感的ML推理场景。
- **在ML中的应用**：无服务器计算适用于：预处理（在发送给模型前调整图像尺寸）、后处理（格式化模型输出并发送通知）、编排（新数据到达时触发训练流程）以及轻量级推理（对冷启动容忍度较高的小型模型）。
- 无服务器计算**不适合**用于：GPU推理（大多数无服务器平台不支持GPU）、长时间运行的训练任务（Lambda的超时时间为15分钟）或有状态服务（调用之间无法保留状态）。

## 成本管理

- 云成本是ML团队首要关注的运营问题。单台H100实例每小时成本约为8美元；64 GPU的训练任务每小时成本约为500美元；持续一个月的训练任务成本可达36万美元。成本优化属于工程范畴，而非单纯的会计工作。
- **抢占式/竞价实例**：云提供商以60–90%的折扣出售闲置算力。提供商可在提前30秒至2分钟通知的情况下回收这些实例。适用于：容错性强的训练（频繁保存检查点，并在新实例上恢复）、批量推理及数据预处理。不适用于对延迟敏感的服务（中断即意味着停机）。
- **预留实例**：承诺使用1–3年可获得30–60%的折扣。适用于负载稳定的推理服务，且能预估基准负载的场景。
- **自动扩缩容**：高峰时段扩容，夜间或周末缩容。一个在高峰时需要10个GPU、夜间仅需2个GPU的模型服务器，通过自动扩缩容可比全天候运行10个GPU节省约60%的成本。
- **合理选型**：不要用H100来运行在A10G上就能正常运行的7B参数模型。应根据工作负载匹配合适的GPU。可利用性能分析（第16章）来确定最佳GPU型号。
- **存储成本**：对象存储价格低廉（S3 Standard为0.023美元/GB/月），但容易累积。若团队为每个实验保存100个大小为10 GB的检查点，共进行50次实验，则会累计产生50 TB数据，每月存储费用达1,150美元。应设置生命周期策略以自动删除旧检查点。

## 多区域部署

- 对于面向全球的ML系统（服务于全世界用户），若仅在一个区域部署，会导致远端用户延迟较高（东京用户访问美国服务器会产生约150毫秒的网络往返时间），且存在单点故障风险（该区域宕机将导致整个服务中断）。
- **多区域部署模式**：
- **主备模式**：由一个主要区域处理所有流量。次要区域处于热备份状态（数据已复制，随时可接收流量）。一旦主要区域发生故障，DNS会切换到次要区域。故障切换期间的停机时间为30秒到几分钟。

- **双活模式**：两个区域同时处理流量。用户会被路由到最近的区域。两个区域的数据都是最新的（异步或同步复制）。单个区域发生故障时不会出现停机时间——流量会自动重新路由。

- **数据复制**：这是难点所在。模型权重可以轻松复制（复制到每个区域的S3中）。特征存储数据必须在可接受的延迟范围内进行复制。用户数据可能受**数据驻留要求**限制（例如GDPR规定：欧洲用户数据必须留在欧洲境内）。

- **GPU云定价对比**（估算值，2026年）：

| GPU | AWS | GCP | Azure | 典型用途 |
| ----- || ----- || ----- || ------- || ------------- ||
| A10G（24 GB） | 1.00美元/小时（g5） | 0.90美元/小时 | 0.90美元/小时 | 小型模型推理 |
| A100（80 GB） | 4.10美元/小时（p4d） | 3.70美元/小时 | 3.40美元/小时 | 训练、大型模型推理 |
| H100（80 GB） | 8.00美元/小时（p5） | 7.50美元/小时 | 7.00美元/小时 | 前沿模型训练 |
| TPU v5e | 不适用 | 1.20美元/小时 | 不适用 | 大规模JAX训练 |

- 抢占式/竞价实例的价格通常比上述价格低60-70%。具体价格会因地区和可用性而异。

## 基础设施即代码

- **IaC**通过版本控制的配置文件来定义基础设施（虚拟机、网络、数据库、K8s集群）。无需在AWS控制台中点击按钮，只需编写描述需求的代码，再由工具自动创建相应资源。

- **Terraform**（HashiCorp）：标准的IaC工具。支持所有主流云服务商。采用声明式方式：你只需描述期望的状态，Terraform便会自动决定需要创建、修改或删除哪些资源以达到该状态。

```hcl
# main.tf — create a GPU VM for inference
resource "aws_instance" "model_server" {
  ami           = "ami-0abcdef1234567890"  # Deep Learning AMI
  instance_type = "g5.xlarge"               # A10G GPU

  tags = {
    Name = "model-server-prod"
  }
}

resource "aws_s3_bucket" "model_weights" {
  bucket = "my-model-weights-prod"

  versioning {
    enabled = true
  }
}
```

```bash
terraform init      # download provider plugins
terraform plan      # show what will change
terraform apply     # create the infrastructure
terraform destroy   # tear it all down
```

- **为什么IaC很重要**：可重复性（通过代码重新创建整个基础设施）、审计功能（Git历史记录能显示谁修改了什么）、灾难恢复（利用相同的配置在不同地区重建基础设施），以及环境一致性（开发、预发布和生产环境使用相同的模板，仅参数不同）。

- **Pulumi**：类似于Terraform，但使用真正的编程语言（Python、TypeScript、Go）而非HCL。当基础设施逻辑较为复杂时（涉及条件判断、循环和动态配置），Pulumi尤为有用。

## 大规模基础设施

_构建能够服务数百万用户的系统仅靠一台服务器远远不够。本文档涵盖了可扩展性模式、分布式系统基础、微服务、数据管道、数据库扩展、搜索与向量系统、可观测性、可靠性工程以及CI/CD等内容。_

- 每秒处理1个请求的模型可以在笔记本电脑上运行。而要达到每秒处理10万个请求且可用性达到99.9%的水平，则需要分布式系统、自动故障转移机制以及精心设计的数据管道。本文档介绍了填补这一差距的相关模式。

## 可扩展性

- **纵向扩展**（Scale Up）：更换性能更强的机器。配备更多的CPU、内存和GPU。这种方式简单，但存在硬性限制（即现有最大规格的机器），且存在单点故障风险。

- **横向扩展**（Scale Out）：增加更多机器。每台机器负责处理一部分流量。这种方式没有单机性能限制，但需要负载均衡（参见文档01）、数据分区以及分布式状态管理。

- **无状态服务**默认支持横向扩展。只需在负载均衡器后添加更多实例即可。那种在启动时加载权重并独立处理请求的模型推理服务器属于无状态服务——任何实例都能处理任意请求。

- **有状态服务**（如数据库、键值缓存、特征存储）则较难扩展。状态必须被分区到多台机器上（分片，参见文档01），并通过复制来确保容错能力。

- **可扩展性公式**：对于一个由$n$台服务器组成的系统：
- **理想情况**：吞吐量呈线性增长（$n$台服务器 → 吞吐量增加$n$倍）。
- **实际情况**：由于协调、负载均衡和数据传输带来的开销，吞吐量呈次线性增长。阿姆达尔定律（第13章）同样适用：串行部分（共享状态、协调操作）会限制系统的加速比。

## 分布式系统

- **分布式系统**是由多台机器协同工作以提供服务的系统。其核心挑战包括：

- **网络分区**：机器之间并非总能正常通信。可能出现网线被切断、交换机故障或数据中心断电等情况。系统必须能够应对局部故障。

- **时钟偏移**：不同机器的时钟并不一致。“事件A在机器1上发生于10:00:01”与“事件B在机器2上发生于10:00:01”并不意味着它们同时发生。**逻辑时钟**（如Lamport时间戳、向量时钟）能在不依赖物理时钟的情况下确定事件顺序。

- **共识机制**：多台机器如何就某个值达成一致（例如确定谁是领导者）？**Raft**是常用的共识算法。集群中的节点会选出一名领导者，由领导者负责所有写操作；若领导者失效，其余节点会重新选举新领导者。该系统需要多数节点（5个节点中需至少3个）才能正常运行，因此能容忍$\lfloor(n-1)/2\rfloor$个节点故障。

- **分布式锁**：用于确保只有一台机器能执行关键操作。**Redlock**（基于Redis）可在多个Redis实例中获取锁；只有当大多数实例都授予锁时，才算获取成功。它常用于防止模型重复部署，或确保只有一个训练任务能写入检查点。

## 微服务

![微服务机器学习架构：API网关将请求路由至特征服务、模型服务和日志服务，各服务拥有独立的数据库，并通过消息队列相互连接](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/microservices_architecture.svg)

- **微服务**将系统拆分成多个小型且可独立部署的服务。每个服务负责一个特定的领域：

```text
┌─────────────┐  ┌──────────────┐  ┌─────────────┐
│ API Gateway │→ │ Feature Svc  │→ │ Feature DB  │
└─────────────┘  └──────────────┘  └─────────────┘
       │
       ├────────→ ┌──────────────┐  ┌─────────────┐
       │          │ Model Svc    │→ │ Model Store │
       │          └──────────────┘  └─────────────┘
       │
       └────────→ ┌──────────────┐  ┌─────────────┐
                  │ Logging Svc  │→ │ Log Store   │
                  └──────────────┘  └─────────────┘
```

- **优点**：独立部署（更新模型服务时无需改动特征服务），独立扩展（根据请求负载扩展模型服务器，根据特征存储读取速率扩展特征服务器），技术自由（模型服务用Python编写，特征服务用Go编写）。

- **缺点**：网络开销（每次服务调用都涉及网络往返），复杂性（调试需跨越多个服务），数据一致性问题（无法跨服务事务处理）。

- **服务发现**：API网关如何找到模型服务？可选方案包括：基于DNS的方式（每个服务注册一个DNS名称）、K8s服务（内置支持）或服务注册中心（如Consul、Eureka）。

- **Saga模式**：对于跨越多个服务的操作（创建用户 + 分配资源 + 发送欢迎邮件），可采用Saga模式：一系列本地事务，一旦某一步失败则执行补偿操作。

## 数据管道

- 机器学习系统需要处理海量数据。**数据管道**负责移动、转换并提供这些数据：

### 批处理

- 定期处理大量数据（每小时或每天）。

- **MapReduce**：最初的批处理范式。先映射（独立转换每条记录）→ 洗牌（按键分组）→ 归约（对每组数据进行聚合）。概念简单但实现繁琐。

- **Apache Spark**：现代批处理引擎。内存计算（迭代算法速度比MapReduce快100倍）。支持SQL、DataFrame以及机器学习管道。是大规模特征工程的标准工具。

- **示例**：为推荐系统计算用户特征。输入：过去30天内的10亿条用户行为事件。输出：1亿个用户特征向量。每天作为Spark作业运行，结果存入特征存储。

### 流处理

- 数据到达时即实时处理（延迟低于1秒）。

- **Apache Flink**：领先的流处理引擎。支持精确一次处理、事件时间处理（按事件发生时间而非到达时间处理）以及窗口操作（滚动窗口、滑动窗口、会话窗口）。

- **Kafka Streams**：内置于Kafka的轻量级流处理工具。适用于简单的转换操作（过滤、聚合），无需单独部署集群。

- **示例**：实时欺诈检测。每笔信用卡交易都是一条Kafka事件。Flink作业会实时计算相关统计数据（交易频率、位置变化），并在100毫秒内标记异常。

### Lambda架构

- 结合批处理和流处理。**批处理层**提供准确且全面的结果（但有延迟）；**快速层**提供近似的实时结果；**服务层**则将两者合并。

- 实际上，如今许多团队采用**Kappa架构**：仅使用流处理，将流视为唯一数据源。由于流可重放（Kafka会保留事件），因此可以通过重放流来模拟批处理。

## 机器学习训练基础设施

- 训练前沿模型（参数规模超过1000亿）是一项大规模基础设施挑战：需要数千个GPU连续运行数月，消耗兆瓦级电力，生成拍字节级数据，成本高达数千万美元。基础设施的好坏直接决定训练能否成功。

### GPU集群

- 训练集群是由高速网络连接的GPU服务器集合。主要组件如下：

![GPU集群：每个节点配备8个通过NVLink连接的GPU，节点之间通过InfiniBand以胖树拓扑相连，可扩展至64到16,000个以上GPU](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/gpu_cluster_topology.svg)

- **GPU服务器（节点）**：每台服务器配备4–8个GPU。典型配置为：8 × H100 GPU、2 × AMD EPYC CPU、2 TB内存、30 TB NVMe SSD。节点内的GPU通过**NVLink**连接（H100上每个GPU的带宽达900 GB/s），其速度比PCIe快30倍。

- **集群规模**：小型训练集群包含64–256个GPU（8–32个节点）；前沿模型训练集群则需4,000–32,000个GPU（500–4,000个节点）。Meta的Llama 3使用了16,384个H100 GPU；Google则在拥有8,000多个芯片的TPU集群上进行训练。

- **粗略估算**：训练一个700亿参数的模型需花费约200万美元的计算成本；训练400亿参数以上的前沿模型则需5000万至1亿美元。仅集群硬件本身在H100价格下就需花费5亿至10亿美元（每颗H100 GPU售价3万美元，16,000颗即需4800万美元）。

### 网络拓扑

- GPU节点间的网络是最关键的基础设施组件。如果GPU之间无法快速交换梯度信息，它们就会因等待通信完成而闲置。

- **InfiniBand**是GPU集群网络的标准。NVIDIA的**Quantum-2 InfiniBand**每端口带宽可达400 Gb/s。每个节点通常配备8个InfiniBand端口（每个GPU对应一个端口），因此每个节点的双向总带宽可达400 GB/s。

- **RDMA**（远程直接内存访问）：InfiniBand支持RDMA技术，可在不同节点的GPU内存之间直接传输数据，无需经过CPU。这将延迟从约100微秒（TCP协议）降至约1微秒，对于高效的梯度汇总操作至关重要（详见第6章）。

- **网络拓扑至关重要**：**胖树拓扑**（Clos网络）能提供完整的双向带宽（任意GPU都能以全速与其他GPU通信）。较便宜的拓扑结构（如**轨道优化型**、**3D环形拓扑**）虽然带宽较低但成本更低。拓扑结构必须与并行策略相匹配：
- **数据并行**：所有GPU间进行梯度汇总 → 需要高双向带宽（胖树拓扑）。
- **张量并行**：同一节点内的GPU间通信 → 由NVLink处理（无需网络支持）。
- **流水线并行**：相邻流水线阶段间的通信 → 只需特定节点对之间的带宽（轨道优化型即可满足需求）。

- **以太网替代方案**：**RoCE v2**（融合以太网上的RDMA）可在标准以太网基础设施上实现RDMA功能。虽然成本低于InfiniBand，但延迟更高且易拥塞。Google在某些TPU集群中采用了RoCE技术。Ultra Ethernet联盟正在开发用于人工智能工作负载的无损以太网。

### 训练所需的存储

- 训练过程需要三个存储层级：
- **数据集存储**：训练语料库（1–100 TB的文本数据，或拍字节级的多模态数据）。存储在分布式文件系统或对象存储中。必须支持高吞吐量的顺序读取（数据加载器以大批量方式读取数据）。**Lustre**和**GPFS**是常见的高性能计算文件系统；云端的替代方案包括AWS的**FSx for Lustre**和GCP的**Filestore**。

- **检查点存储**：定期保存训练状态（模型权重、优化器状态及调度器状态）。对于采用混合精度且使用Adam优化器的70B参数模型而言，每个检查点约占560 GB（70B × 4字节 × 2，用于优化器状态）。若每小时保存一次检查点，运行3个月将产生约2000个检查点，总大小达1.1 PB。实践中只会保留最新的N个检查点，旧的检查点会被删除。存储速度必须足够快，以免检查点操作显著拖慢训练进程。

- **日志与指标**：实验跟踪数据（损失曲线、学习率调度、梯度范数等）。这些数据量相对较小，但需实时写入。W&B、MLflow或TensorBoard可满足此类需求。

- **存储瓶颈**：一个拥有16,000个GPU的集群在加载训练批次时，需要持续读取约100 GB/秒的数据。如果文件系统无法维持此吞吐量，GPU就会因等待数据而闲置。因此，数据管道优化（预取、缓存，以及使用WebDataset或Mosaic Streaming进行格式优化）至关重要。

### 作业调度

- GPU集群需为多个团队和项目提供服务。**作业调度器**负责为训练作业分配GPU资源：

- **SLURM**：标准的高性能计算作业调度器。用户提交作业时需指定GPU数量、内存及时间限制。SLURM负责分配资源并管理队列。它支持基于优先级的调度、抢占机制以及团队间的公平共享分配。

- **带GPU调度的Kubernetes**（第18章文件02）：这是一种云原生方案。K8s的GPU设备插件将GPU作为可调度资源。**Volcano**和**Run:ai**则增加了针对机器学习的调度功能：批量调度（一次性为作业分配所有所需GPU，而非逐个分配）、优先级队列以及GPU时间共享。

- **调度挑战**：
- **碎片化**：一个拥有1000个GPU的集群中可能有200个空闲GPU，但它们分散在50个节点上（每个节点仅4个空闲GPU）。此时，即使总GPU数量足够，需要128个连续GPU的作业也无法运行。**碎片整理**（迁移作业以整合空闲GPU）或**拓扑感知调度**（分配连接性良好的GPU）可解决此问题。
- **优先级与抢占**：紧急实验应能抢占低优先级作业。但若抢占一个已运行两天的训练作业，会造成计算资源的浪费。调度器必须在优先级与效率之间取得平衡。
- **公平共享**：各团队应随时间获得其分配的计算资源份额，即便某个团队提交的作业数量超出其份额。

### 容错机制

- 在数千个GPU上运行数月的情况下，硬件故障并非罕见现象——而是常态。一个拥有16,000个GPU的集群，两次故障之间的平均时间间隔通常以小时计，而非月为单位。

- **常见故障类型**：GPU内存错误（可纠正和不可纠正）、NVLink故障（节点内GPU间通信中断）、InfiniBand链路故障（节点间通信中断）、节点崩溃（内核崩溃、电源故障）以及存储故障（磁盘或控制器故障）。

- **检查点机制**是主要的防护措施。每N步保存完整的训练状态（模型、优化器、数据加载器位置）。发生故障时：确定故障节点，替换或移除该节点，然后从最新的检查点重新开始训练。故障造成的损失仅限于上次检查点到故障发生期间的计算资源消耗。

- **检查点频率的权衡**：频繁检查点（每10分钟一次）可减少故障造成的计算浪费，但会拖慢训练速度（保存560 GB数据需要时间）；不频繁检查点（每2小时一次）虽然训练更快，但故障时会浪费多达2小时的计算资源。大多数团队选择每20–60分钟进行一次检查点。

- **弹性训练**：现代框架（如PyTorch Elastic、DeepSpeed）支持无需重启即可调整训练规模。如果500个节点中有2个发生故障，训练仍可在剩下的498个节点上继续；故障节点被替换后，训练会在它们重新上线时自动将其纳入。

- **健康监测**：持续监控所有GPU的状态（温度、内存错误、计算吞吐量）、网络链路（丢包率、延迟）以及存储系统（吞吐量、错误率），并在出现异常时自动报警。部分集群会定期执行GPU健康检查（短时计算测试），以便提前发现性能下降的硬件。

- **大规模训练实例**：Meta训练Llama 3模型时使用了16,384个H100 GPU，耗时54天，期间发生了约466次作业中断。实际有效训练时间仅占时钟时间的约90%——另有10%的时间被用于故障处理与恢复。能够实现90%利用率（而非50%或70%）的基础设施，正是能够训练前沿模型的组织与无法做到这一点的组织之间的区别所在。

### 成本与效率

- 训练基础设施的成本主要由GPU运行时长决定：

| 组件 | 占总成本比例 |
| ------ || -------------- ||
| GPU计算 | 70–80% |
| 网络（InfiniBand） | 10–15% |
| 存储 | 5–10% |
| 冷却与供电 | 5–10% |

- **GPU利用率**（模型浮点运算利用率，MFU）衡量的是GPU理论峰值性能中实际用于有效计算的比例。H100的峰值性能为989 TFLOPS（FP8）。达到40–50%的MFU属于良好水平；50–60%则为优秀。利用率不足的原因包括：通信开销（如All-Reduce操作、流水线气泡）、内存带宽限制，以及检查点和数据加载期间的闲置时间。

- **提升MFU的方法**：让计算与通信重叠（第6章），采用高效的注意力机制（如Flash Attention，第16章），优化数据加载过程以避免GPU闲置，减少检查点开销（采用异步检查点机制，先将检查点写入高速NVMe存储，再后台复制到持久化存储）。
- **自建 vs 购买**：在小规模场景下（<256个GPU），云服务更便宜（无需前期成本，按小时计费）。在大规模场景下（>1000个GPU且持续使用6个月以上），自购硬件更划算（3年内的总体拥有成本可降低约2-3倍）。大多数人工智能公司采用混合模式：用自有集群进行持续训练，用云服务应对突发需求和实验性开发。

## 数据库扩展

- **只读副本**：将读请求路由到主数据库的副本上。主库负责写操作，副本负责读操作。由于大多数工作负载以读为主（读操作占比超过95%），因此读吞吐量会随着副本数量的增加而线性提升。

- **分区**（分片，参见文件01）：将数据拆分到多个数据库中。每个分区相互独立，从而实现并行读写。难点在于跨分区查询（即合并来自不同分片的数据）。

- **连接池**：数据库的连接能力有限。连接池（如PostgreSQL的PgBouncer）可在不同请求之间复用连接，防止数百个服务实例同时连接时导致连接耗尽。

## 搜索与向量系统

### 文本搜索

- **倒排索引**：文本搜索的基础。为每个单词存储包含该单词的文档列表。查询时，只需取各查询词对应的列表交集。**Elasticsearch**是行业标准：支持分布式、实时处理、全文检索、聚合分析及地理空间查询。

- **BM25**：标准的文本检索评分函数。根据词频、逆文档频率以及文档长度归一化来给文档打分。虽然简单却十分有效——在关键词密集型查询中，其效果仍可与神经网络方法相媲美。

### 向量搜索

- **向量数据库**用于存储嵌入向量（高维向量），并支持快速的**近似最近邻（ANN）**搜索。给定一个查询向量，即可找出与其最相似的$k$个存储向量。

- **FAISS**（Facebook AI相似度搜索）：一个用于ANN搜索的库（并非数据库）。支持多种索引类型：
- **Flat**：精确搜索，时间复杂度为$O(n)$。适用于小型数据集或作为基准测试。
- **IVF**（倒排文件索引）：将向量划分为若干簇，仅搜索最近的簇。每次查询的时间复杂度为$O(n/k)$。
- **HNSW**（分层可导航小世界图）：基于图的索引方式。构建分层图结构，从粗粒度逐步细化搜索。速度极快且精度高，是大多数应用的默认选择。
- **乘积量化（PQ）**：将向量压缩为紧凑编码，以实现内存高效的搜索。以牺牲一定精度为代价来换取更低的内存占用。

- **托管型向量数据库**：Pinecone、Weaviate、Milvus、Qdrant。它们能够处理FAISS无法实现的扩展、复制及实时更新功能。

- **对于RAG**（检索增强生成）：用户查询 → 通过文本编码器生成嵌入向量 → 在向量数据库中搜索相关文档 → 将检索到的文档附加到LLM提示词中。检索质量直接决定了LLM生成结果的质量。

## 可观测性

- **可观测性**是指根据系统的外部输出来判断其内部运行状态的能力。它包含三大支柱：

### 日志记录

- **结构化日志**（JSON格式）便于搜索和解析。非结构化日志（如“ERROR: 某操作失败”）则难以处理。应始终记录：时间戳、服务名称、请求ID（用于跨服务追踪）、严重程度以及相关上下文信息。

- **ELK栈**（Elasticsearch、Logstash、Kibana）：标准的日志处理流程。Logstash负责收集和转换日志，Elasticsearch负责索引，Kibana则用于可视化和搜索。

### 指标监控

- **指标**是随时间变化的数值测量结果：请求速率、错误率、延迟百分位数、GPU利用率、队列深度等。**Prometheus**用于从服务中采集指标；**Grafana**则通过仪表盘展示这些指标并提供告警功能。

- 针对服务的**RED方法**：**R**ate（每秒请求数）、**E**rrors（错误率）、**D**uration（延迟）。需对每个服务监控这三项指标。

- 针对资源的**USE方法**：**U**tilisation（利用率）、**S**aturation（队列深度）、**E**rrors。需对每个资源（CPU、GPU、内存、磁盘、网络）监控这三项指标。

### 链路追踪

- **分布式追踪**用于跟踪单个请求在多个服务间的传递过程。例如：用户请求先到达API网关 → 特征服务 → 模型服务 → 后处理环节。一次**追踪**会记录每个环节的耗时，从而揭示延迟产生的位置。

- **OpenTelemetry**：追踪、指标和日志领域的开放标准。只需对代码进行一次埋点，即可将数据导出到任何后端（如Jaeger、Zipkin、Datadog）。

## 可靠性

- **SLO**（服务等级目标）：期望达到的可靠性指标。例如：“99.9%的请求能在200毫秒内完成。”这设定了一个具体的错误预算：允许有0.1%的请求（每月约43分钟）响应缓慢或失败。

- **SLI**（服务等级指标）：实际的测量值。例如：“过去5分钟内的第99百分位延迟。”

- **SLA**（服务等级协议）：具有约束力的合同承诺。例如：“若可用性低于99.95%，客户可获得补偿。”

- **错误预算**：如果SLO为99.9%而你已达到99.99%，则说明还有余地实施风险较高的变更（如部署新模型、迁移数据库）；若仅为99.85%，则应暂停所有变更并专注于提升可靠性。错误预算将可靠性从一个抽象目标转化为可量化的资源。

- **混沌工程**：故意引入故障（如关闭服务器、增加网络延迟、损坏数据）以测试系统能否正确处理。Netflix的Chaos Monkey会随机终止生产环境中的实例。若系统仍能正常运行，说明其具备韧性；若崩溃，则意味着你提前发现了漏洞，避免了用户受到影响。

## CI/CD

- **持续集成**：自动构建并测试每一次代码变更。每次提交都会触发代码检查、类型检查、单元测试及集成测试。一旦有任何一项测试失败，该变更就会被拒绝。这样就能在代码进入生产环境前发现并修复漏洞。

- **持续部署**：自动部署通过CI测试的变更。部署策略包括：
- **蓝绿部署**：运行两个完全相同的环境（蓝色=当前版本，绿色=新版本）。可即时将流量从蓝色环境切换到绿色环境。如果绿色环境出现故障，则立即切换回蓝色环境（即时回滚）。

- **金丝雀发布**：将一小部分流量（1-5%）导向新版本，同时监控是否存在错误。若各项指标表现良好，则逐步增加流量。这种方式能限制不良部署所带来的影响范围。

- **功能开关**：部署新代码但将其隐藏在开关之后。先为一部分用户启用该开关（内部测试人员，然后是Beta用户，最后面向所有人）。这样可将部署（代码已上线）与发布（用户看到该功能）分离开来。

- 对于机器学习而言：CI/CD流程中包含针对模型的特定步骤。模型变更会触发以下操作：单元测试（数据形状检查、梯度验证）、在保留数据集上进行评估（准确率不得下降）、影子部署（让新模型与旧模型同时运行并对比输出结果），以及逐步发布（从1%流量逐步增加到100%）。

### 问题定义

- 在接触数据或模型之前，需明确以下内容：
- **要预测什么？**（点击概率、下一个令牌、物体边界框）
- **用户是谁？**（最终用户、内部分析师、其他机器学习模型）
- **有哪些约束条件？**（延迟需低于100毫秒，可离线批量处理，必须在设备上运行）
- **业务指标是什么？**（收入、用户参与度、准确率），以及机器学习指标与这些指标之间的关系
- **基准是什么？**（启发式方法、基于规则的系统、现有模型）——必须优于这些基准，才能证明使用机器学习系统的必要性

- **常见错误**：在未理解问题之前就直接设计模型架构。“我们应该使用Transformer模型”并非有效的系统设计思路。而“我们需要在200毫秒内预测1000万个候选项的点击概率，因此需要采用两阶段系统：先快速检索，再通过小型排序模型进行筛选”才是正确的思路。

## 数据管理

### 数据收集与标注

- **显式标注**：由人工对数据进行标注（点击/未点击、物体边界框、对话质量评分）。成本较高（根据复杂程度，每个标注的成本约为0.02美元到10美元），速度较慢，且具有主观性。

- **隐式标注**：从用户行为中推断出标注信息。例如点击行为、停留时间、购买行为、跳过行为等。这类标注成本低且数量多，但存在噪声（点击并不一定意味着满意，跳过也不一定意味着不喜欢）。

- **程序化标注**（Snorkel）：编写标注函数（利用启发式规则、正则表达式或现有模型）对每个样本进行评分，再通过统计方法汇总得分，从而得出概率性标注结果。该方法能够处理数百万个样本，且准确率尚可。

- **主动学习**：模型会识别出自己最不确定的样本，并请求人工对这些样本进行标注。这样可以提高标注效率：1000个经过主动选择的标注样本，其效果相当于10,000个随机选取的标注样本。

### 数据质量

- **数据验证**：需检查每批输入数据的格式是否正确（是否存在缺失字段、类型是否错误）、数据分布是否发生变化（平均值是否有显著变化），以及数据量是否异常（预期有100万行数据，实际只有50万行）。

- **Great Expectations**和**TFX Data Validation**等工具可用于设定数据标准，一旦数据不符合标准就会发出警报。

- **数据版本控制**：每次训练过程都应能够重复执行。**DVC**（第15章）可用于同时管理代码和数据文件。每个数据集版本都有一个哈希值，训练配置会引用该哈希值。

### 特征存储

![特征存储：相同的特征计算结果既可用于离线存储（用于训练），也可用于在线存储（用于服务），从而避免训练与服务之间的差异](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/feature_store.svg)

- **特征存储**（第15章）可为训练和服务提供一致的特征数据。相关概念包括：

- **离线特征**：通过批处理流程（如Spark）计算得出，存储在数据仓库中。用于训练及批量推理。例如，用户30天内的平均会话时长、商品的累计购买次数。

- **在线特征**：实时计算或预先计算好，存储在低延迟存储系统中（如Redis、DynamoDB），用于实时推理。例如，用户最近的5次操作、当前购物车中的物品。

- **训练与服务的差异**：如果训练和服务的特征计算方式不同，模型在推理时得到的特征值就会与训练时的不同。特征存储通过统一计算方式来消除这一差异。

## 训练基础设施

- 对于本书的读者而言，分布式训练的相关内容已在第6章中详细讲解（数据并行、模型并行、混合精度、扩展定律）。此处我们重点讨论**系统层面**的内容。

- **实验跟踪**（W&B、MLflow——第15章）：每次训练都会记录超参数、各项指标、Git提交信息、数据版本以及硬件信息。这相当于机器学习领域的模型版本控制机制。

- **超参数调优**：自动搜索最优超参数。常用方法包括网格搜索（虽然全面但成本高）、随机搜索（效果往往不错）、贝叶斯优化（对目标函数进行建模，选择最有可能带来改进的参数值），以及**ASHA**算法（异步逐步减半法：启动多个试验，提前终止表现不佳的试验）。

- **训练流程编排**（Airflow、Kubeflow——第15章）：自动化处理数据准备→训练→评估→部署的整个流程。可设置每日自动重新训练，并在出现故障时发出警报。

## 模型评估

### 离线评估

- **保留的测试集**：在模型训练过程中从未见过的数据上进行评估。这是一种标准做法，但如果测试集无法代表实际生产环境的数据，那么评估结果可能会具有误导性。

- **分组评估**：按用户群体特征、内容类型、语言、时间周期等将数据分成不同的子组进行评估。一个整体准确率为95%的模型，可能在某个特定少数群体上的准确率仅为70%，这是不可接受的。

- **回测**：对于时间序列或顺序预测任务，需按照时间顺序使用历史数据来进行评估。先用时间$t$之前的数据训练模型，再用时间$t$到$t+\Delta t$之间的数据来评估模型。这样可以避免使用未来数据影响训练结果。

### 在线评估

![A/B测试：将用户随机分为对照组（旧模型）和实验组（新模型），通过统计方法比较各项指标](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/ab_testing.svg)

- **A/B测试**：将真实用户流量随机分为对照组（使用旧模型）和实验组（使用新模型），然后通过统计方法比较业务指标（如收入、用户参与度、留存率）的差异。这是评估机器学习模型改进效果的标准方法。

- **样本量**：需要足够多的数据才能检测出预期的效果。例如，若希望点击率提升0.1%，则需要数百万次的展示次数才能获得具有统计意义的成果。

- **测试时长**：至少需要运行一个完整周期（大多数产品为1-2周），以便考虑不同日期带来的影响。

- **监控指标**：除了目标指标外，还需监控那些不应发生变化的指标（如页面加载时间、错误率、崩溃率）。如果一个模型虽然提升了收入，但同时也增加了崩溃率，那实际上仍是负面的效果。
- **影子部署**：在生产环境中同时运行旧模型和新模型。两者都会接收相同的请求，但只有旧模型的预测结果会提供给用户。通过比较两种模型的输出，可以发现错误和质量问题，且不会对用户造成影响。

- **混合处理**：对于排序类问题，将旧模型和新模型的预测结果混合在一起，形成一份列表。用户会看到这份混合后的列表，进而可以判断哪种模型的结果更受用户青睐。与A/B测试相比，这种方法的所需用户数量更少。

## 模型服务

### 批量处理与实时处理

- **批量推理**：预先为所有可能的输入计算出预测结果，并将其存储在数据库或缓存中，之后从缓存中提供这些预测结果。这种方法适用于输入范围有限的情况（适合为所有用户生成每晚的预测结果）、数据时效性要求不高的情况（每日预测即可），以及对延迟容忍度较高的场景。

- **实时推理**：针对每个请求按需计算预测结果。这种方法适用于输入范围无限的情况（任何用户的查询都适用）、数据时效性非常重要的情况（需要立即对当前查询进行预测），以及对延迟要求极低的情况。

- 许多系统会同时使用这两种方法：批量处理用于预先生成一批候选预测结果（成本较低，可覆盖80%的请求），而实时处理则用于处理剩余的请求（成本较高，但能处理那些特殊的查询以及新用户的请求）。

### 模型版本管理

- **模型注册表**（如MLflow、W&B、SageMaker）用于存储经过训练的模型及其相关元数据：
- 版本号及训练日期。
- 训练配置及数据版本。
- 评估指标（准确率、延迟时间、内存使用情况）。
- 模型的发展阶段：开发阶段 → 测试阶段 → 生产阶段 → 存档阶段。

- **回滚机制**：如果新模型在生产环境中的性能变差，可以立即恢复到之前的版本。借助模型注册表，这一操作只需点击一下即可完成。

## 特征工程

- **特征工程**的作用是将原始数据转换为模型所需的输入格式。在机器学习中，特征工程往往具有最大的影响力：更好的特征能够提升所有模型的性能，而模型的性能则受到其所接收到的特征质量的限制。

### 在线特征与离线特征

- **离线特征**是预先计算好的，且变化较慢（如用户的人口统计信息、30天内的汇总数据）。这类特征是通过批量处理流程（如Spark）计算出来的，然后存储在特征存储系统中。

- **在线特征**反映的是当前的状态，变化速度很快（如购物车中的商品、用户最近的操作、当前位置等信息）。这类特征是从事件流中实时计算得出的，或者从快速检索系统中获取的。

- **特征时效性**：有些特征需要保持极高的时效性（如欺诈检测：根据最近5笔交易，判断当前这笔交易是否异常？），而另一些特征则可以稍滞后一些（如推荐系统：根据用户的历史行为，判断他们喜欢哪些类型的作品？）。时效性更高的特征，其计算和传输成本也更高。

### 常见的特征类型

- **计数特征**：在特定时间窗口内发生的事件数量（如过去7天的购买次数、过去24小时的登录次数）。
- **嵌入特征**：为分类变量生成的嵌入向量（如用户嵌入、商品嵌入、查询嵌入）。这类特征是双塔模型及类似架构的输入数据。
- **交叉特征**：两个或多个特征的组合（如用户年龄×商品类别），可用于捕捉单个特征无法体现的交互效应。
- **时间特征**：自上次操作以来的时间、星期几、当前时间等，用于捕捉时间相关的模式。
- **聚合特征**：某个数值特征在某个群体中的平均值、中位数、最小值、最大值及标准差（如该卖家所售商品的平均评分）。

## 机器学习流水线

- 机器学习流水线负责协调从数据准备到模型部署的整个工作流程：

```text
Data ingestion → Validation → Feature engineering → Training → Evaluation → Registration → Deployment → Monitoring
```

- 每一步都是协调器中的某个任务（Airflow、Kubeflow、Metaflow——见第15章）。该数据管道：
- 按预定时间表运行（定期重新训练），或在有新数据时触发运行。
- 具有可重复执行性（重新运行会得到相同结果）。
- 包含重试机制（如果特征计算失败，会以逐渐延长的间隔尝试3次）。
- 会生成各种输出结果（训练好的模型、评估报告、特征统计信息），这些结果会被版本化管理并存储起来。

- **Metaflow**（由Netflix/Outerbounds开发）特别适合用于机器学习任务：它能够同时对代码、数据和模型进行版本管理，支持在本地和云端使用相同的代码进行开发，同时还可与K8s和AWS集成。

## 监控

- 第15章已经介绍了监控的基本知识（Prometheus、Grafana、警报功能）。这里则重点讨论**针对机器学习系统的特定监控方法**：

### 数据漂移

- 当输入数据的分布与训练数据相比发生变化时，就会出现数据漂移现象。用夏季数据训练出的模型，在冬季数据上可能会表现不佳（因为用户行为和商品可用性都可能有所不同）。

- **检测方法**：通过统计测试来比较输入特征的分布与训练数据的分布：
- **KS检验**（Kolmogorov-Smirnov检验）：用于比较两个经验分布，判断它们是否来自同一个潜在分布。
- **PSI指数**（总体稳定性指数）：用于衡量分布变化的程度。PSI值小于0.1表示分布稳定，0.1–0.25表示有中等程度的变化，大于0.25则表示变化显著。
- **嵌入向量漂移**：通过质心距离或MMD（最大均值差异）来比较新输入数据的嵌入向量分布与训练集的嵌入向量分布。

### 概念漂移

- 当输入与输出之间的关系发生变化时，就会发生概念漂移。此时虽然特征看起来没有变化，但正确的预测结果却不同。例如，文化活动、疫情或产品变动之后，用户的偏好可能会发生变化。

- 概念漂移比数据漂移更难检测，因为它需要带有标签的数据。可以监测一些替代指标，如点击率、转化率、用户满意度得分。如果这些指标持续下降，就说明可能存在概念漂移。

### 模型退化

- 由于多种原因，模型会随着时间的推移而退化：数据漂移、概念漂移、特征处理流程中的错误（某些特征开始返回空值），以及上游数据的变化（第三方API改变了其响应格式）。

- **应对措施**：一旦发现模型退化，应根据其严重程度采取相应行动：
- 轻微情况：使用最新数据重新训练模型（定时重新训练即可解决此问题）。
- 中等程度：找出根本原因（是哪个特征发生了变化？哪些用户群体受到了影响？）。
- 严重情况：立即回退到之前的模型版本，然后再进行调查。

### 反馈循环

- 机器学习系统会形成**反馈循环**：模型的预测会影响用户行为，而这些行为又会成为下一个模型版本的训练数据。这类循环可能是良性的，也可能是恶性的。

- **良性反馈循环**（危险）：推荐系统总是推荐最受欢迎的商品，用户只能看到这些商品，于是他们就会继续点击这些商品；这样一来，模型就会认为这些商品确实更受欢迎，从而导致多样性丧失。模型实际上是在创造那些能验证其偏见的“数据”。

- **恶性反馈循环**（同样危险）：欺诈检测系统能够识别出所有类型的A类欺诈行为，结果就没有A类欺诈行为进入训练数据，下一个模型就无法学会识别A类欺诈，于是A类欺诈又会重新出现。

- **缓解措施**：
- **探索性策略**：向模型展示一些它不确定的商品（比如使用epsilon-greedy算法或Thompson采样），这样就能生成更多样化的训练数据。
- **反事实记录**：不仅要记录用户实际看到的内容，还要记录模型原本会做出的预测。利用反事实数据来消除模型的偏见。
- **保留测试集**：随机将一部分流量不经过模型过滤直接处理。这些未经过滤的数据可以作为评估模型质量的参考。
- **延迟标记**：在将数据用于训练之前，先等待真实的处理结果。今天被推荐的物品，明天用户可能会后悔选择它；对于欺诈检测，也需要等到30–90天的退款周期结束后才能确定结果。

### 嵌入向量表的管理

- 大规模的机器学习系统通常会有包含1亿多个条目的嵌入向量表（每个用户、商品、广告或实体都有一个嵌入向量）。大规模管理这类数据表是一项复杂的系统工程。

- **存储问题**：1亿个实体，每个实体有256维的float16格式数据，总共需要50GB的存储空间。这个容量超过了GPU的内存限制。解决方案包括：将数据存储在CPU内存中，同时利用GPU进行缓存；将数据分散存储在多台机器上；或者使用**哈希嵌入向量**（将实体映射到固定大小的表中，允许出现冲突）。

- **更新问题**：随着模型的重新训练，嵌入向量也会发生变化。要将新的嵌入向量表部署到系统中，需要在不影响现有服务的情况下将50GB的数据加载到内存中，同时还要验证数据的正确性，如果性能指标下降，则需要回退到之前的版本。对于嵌入向量表，可以采用蓝绿部署策略。

- **数据过时问题**：新创建的用户没有对应的嵌入向量（即“冷启动”问题）。解决方案包括：使用默认嵌入向量；通过特征到嵌入向量的模型根据用户的特征生成嵌入向量；或者使用非个性化模型。

### 公平性与偏见

- 机器学习系统可能会系统性地对不同群体做出不同的处理，而这往往反映了训练数据中的偏见。因此，**公平性监控**是一种必要的责任，而非可选功能。

- **需要监控的指标**：
- **人口统计平等性**：不同群体之间的阳性预测率是否有差异？比如性别、种族、年龄等方面的差异。
- **机会平等性**：不同群体之间的真正阳性率是否有差异？例如，招聘系统应该能够同样好地识别出所有群体中的合格候选人。
- **校准性**：如果模型认为A群体的合格概率为0.7，那么A群体中实际上有多少人符合条件？B群体也是如此吗？
- **实际操作步骤**：
- 不仅要依据整体指标，还要对模型在各个子群体上的表现进行评估。
- 在模型评估流程中加入公平性指标——如果某个模型虽然提升了整体准确率，但却损害了某些特定群体的利益，那么就不应将其投入使用，必须先进行审查。
- 记录该模型存在的已知局限性与故障模式。
- 对那些被应用于敏感领域的模型（如招聘、贷款审批、刑事司法、医疗保健等领域）建立相应的审查机制。

## 机器学习设计示例

_学习机器学习系统设计的最佳方式是通过实际案例。本文件介绍了七个完整的设计案例：推荐系统、搜索排序、广告点击率预测、欺诈检测、内容审核、对话式人工智能以及大规模图像搜索。_

- 每个案例都遵循相同的框架：

1. **问题定义**：我们要构建什么系统？用户是谁？存在哪些限制条件？
2. **数据**：我们拥有哪些数据？这些数据是如何收集的？又是如何标记的？
3. **特征**：模型需要哪些特征？
4. **模型**：应采用何种架构和训练方法？
5. **部署**：如何将模型部署并投入使用？
6. **评估**：如何衡量系统的成功程度？
7. **迭代优化**：随着时间推移，我们可以做出哪些改进？

## 1. 推荐系统（例如YouTube、Netflix、Spotify）

### 问题定义（续1）

- **目标**：向用户展示他们可能感兴趣的内容，从而提升用户的参与度（观看时间、收听时间、点击次数）。
- **规模**：用户数量超过10亿，内容数量超过1亿，每秒需要生成超过1万条推荐结果。
- **延迟要求**：整个推荐流程的延迟需低于200毫秒。
- **主要挑战**：可选内容数量极其庞大（1亿条），无法实时为所有用户评估所有内容的适用性。

### 架构：两阶段处理流程

![推荐系统流程图：从1亿条内容中通过初步筛选缩小到1000条，再进一步排序后得到100条候选内容，最终筛选出20条最合适的推荐内容](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/recommendation_pipeline.svg)

```text
100M items → Candidate Generation (fast, coarse) → 1000 candidates
          → Ranking (slow, precise) → 100 ranked items
          → Re-ranking (business rules) → 20 shown to user
```

### 候选项生成

- **目标**：将1亿个物品简化为约1000个候选项。处理速度需达到<50毫秒。
- **双塔模型**：将用户和物品映射到同一个嵌入空间中。用户嵌入用于表示用户的偏好，而物品嵌入则用于反映物品的内容特征。得分即为用户嵌入与物品嵌入的点积。
- **训练过程**：基于（用户、正样本物品、负样本物品）三元组进行对比学习。正样本为用户曾经互动过的物品；负样本则包括随机选取的物品以及那些用户从未互动过的热门物品。
- **服务阶段**：预先计算所有物品的嵌入向量。当收到查询时，先计算用户的嵌入向量，再通过向量数据库中的HNSW算法查找距离最近的1000个物品的嵌入向量。

### 排序

- **目标**：准确地为这1000个候选项打分。允许的处理时间为约100毫秒。
- **模型**：使用深度神经网络（如MLP或Transformer），输入多种特征，包括用户特征（人口统计信息、历史行为、上下文信息）、物品特征（内容、受欢迎程度、新鲜度），以及交叉特征（用户与物品的交互历史、上下文相关性）。
- **输出结果**：预测用户与各物品互动的概率，比如点击概率、观看概率、点赞概率、分享概率等。可以同时考虑多个目标，公式为：$\text{score} = w_1 \cdot P(\text{click}) + w_2 \cdot P(\text{watch}) + w_3 \cdot P(\text{like})$。

### 重新排序

- 应用业务规则：确保多样性（避免连续展示同一创作者的5个视频）、优先展示最新内容、过滤有问题的内容，同时也会向用户展示一些排名较低但可能感兴趣的物品。

### 大致成本估算

- **物品嵌入索引**：1亿个物品 × 256维 × float16格式 = 50GB。使用HNSW索引后，存储开销会增加约2倍，总计约为100GB。这样的数据量可以在拥有128GB内存的单台机器上存储，或者分布在4台各32GB内存的机器上。
- **用户嵌入计算**：每个用户的嵌入向量计算时间约为5毫秒（使用小型MLP模型处理用户特征）。在1万次/秒的查询量下，需要大约50个模型实例来处理这些请求。
- **ANN搜索**：使用HNSW算法从1亿个向量中找出排名前1000的向量，搜索时间约为2毫秒。在1万次/秒的查询量下，每个索引实例可处理约500次查询，因此需要20个这样的实例。
- **排序模型**：1000个候选项，每个候选项的排序时间约为0.1毫秒，因此每次查询的总处理时间为100毫秒。在1万次/秒的查询量下，每秒需要1000 GPU秒的计算能力，也就是说，仅排序功能就需要大约10台A10G级别的GPU。
- **整体基础设施需求**：大约需要20个嵌入索引实例、50个用户嵌入计算服务器、10台用于排序的GPU，再加上缓存系统和负载均衡器。按照云服务的价格计算，每月的成本大约在5万到10万美元之间。

### 新用户/新物品的处理策略

- **新用户**（没有历史交互记录）：首先利用人口统计信息、设备/位置信息以及基于流行度的推荐算法来提供内容。在用户有过5到10次交互之后，再切换到个性化推荐模型。
- **新物品**（没有交互数据）：此时则利用基于内容的特征，如标题、描述、缩略图嵌入向量等来决定如何展示该物品。可以适当选择一部分用户来试用这些新物品，以便快速收集相关数据。如果经过一段时间后这些物品仍然没有得到任何互动，那么它们的排名就会下降。
- **冷启动问题属于系统层面的问题**：特征存储系统必须能够妥善处理缺失的特征（给出默认值而非报错）。在模型训练过程中，也需要考虑缺失的特征的情况（例如在训练时对用户历史特征使用 Dropout 技术，以此模拟新用户的情况）。

### 评估方法

- **离线评估**：使用保留的测试数据集，通过NDCG（标准化折扣累积增益）、召回率@K、精确率@K等指标来进行评估。
- **在线评估**：通过A/B测试来衡量用户的观看时长、日活跃用户数、用户留存率等指标。为了更全面地了解用户留存情况，还可以进行长期A/B测试（数周时间）。

## 2. 搜索排序（例如Google、Bing）

### 问题定义（续2）

- **目标**：根据用户的查询，从数十亿份文档中找出最相关的结果。
- **延迟要求**：总延迟需低于500毫秒，其中检索耗时100毫秒，排序耗时200毫秒，结果渲染耗时100毫秒，再加上其他开销。

### 系统架构：查询理解 → 检索 → 排序

### 查询理解

在开始检索之前，需要对原始查询进行处理，以提升查询结果的准确性：

- **拼写纠正**：将“reccomendation systm”纠正为“recommendation system”。可以使用编辑距离模型，或者基于搜索日志中的错误拼写与正确拼写对训练得到的序列到序列模型来实现这一功能。
- **查询扩展**：通过添加相关术语来提高召回率。例如，将“Python ML”扩展为“Python机器学习scikit-learn pytorch”。可以利用同义词词典、词嵌入向量，或是大型语言模型来生成扩展后的查询词。
- **意图识别**：确定用户的真实需求。例如，“buy Nike shoes”属于交易类需求，应直接显示产品页面；“How does backpropagation work”属于信息查询类需求，应提供相关文章；“facebook.com”则是导航类需求，应直接跳转到该网站。不同的意图应对应不同的检索策略和结果展示方式。
- **实体识别**：从查询中提取出各种实体。例如，“best restaurants near Times Square”中的实体包括地点“Times Square”和实体类型“restaurants”。这类信息可用于引导用户进入基于位置的搜索流程。

### 检索

- **BM25**（传统方法）：基于倒排索引的关键词匹配检索方式。速度快，适用于关键词查询，但无法理解语义（例如“dog food”与“canine nutrition”不会被视为相关）。
- **密集检索**：将查询和文档都转换为嵌入向量（可使用DPR或ColBERT之类的双编码器），然后通过ANN搜索来找到相似的文档。这种方式能够理解语义上的相似性（“dog food”与“canine nutrition”会被视为相关）。虽然速度比BM25慢，但更适合处理自然语言查询。
- **混合检索**：结合BM25和密集检索的优点。BM25用于查找完全匹配关键词的文档，而密集检索则用于查找语义上相似的文档。最后将两种结果合并并去重，从而获得最佳的结果。

### 排序（续1）

- **排序学习**：通过模型为每一对（查询，文档）打分。主要有三种方法：
- **点态排序**：分别为每个文档独立预测其相关性得分。这种方法简单，但无法体现文档之间的相对顺序。
- **配对排序**：判断两个文档中哪个更相关。LambdaMART（基于梯度提升树的模型）是这种方法的典型代表。
- **列表级排序**：直接针对整个排序列表优化，以最大化NDCG等指标的值。这种方法较为复杂，但能得到最好的排序结果。
- **交叉编码器**：一种基于Transformer的模型，以[查询词、文档]作为输入，输出相关性得分。由于能够捕捉到更细微的交互信息，因此比分别对查询词和文档进行编码的双编码器更为准确。不过，对于整个语料库来说其处理速度较慢——仅用于对检索出的前100-1000个候选项进行重新排序。

### 特征

- **查询词特征**：查询词长度、语言类型、意图分类（导航类、信息类、交易类）。
- **文档特征**：PageRank值、内容新鲜度、内容质量评分、域名权威度。
- **查询词-文档特征**：BM25评分、嵌入向量相似度、精确匹配数量，以及历史日志中该（查询词，文档）组合的点击率。

## 3. 广告点击预测

### 问题描述

- **目标**：预测用户点击广告的概率。这一数值决定了在实时竞标中应出价多少。
- **处理规模**：每秒需处理10万次以上的竞标，每次竞标都需在10毫秒内给出预测结果。
- **收入影响**：若点击预测的准确性提高0.1%，就能带来数百万美元的额外收入。

### 架构

- **特征工程**是广告系统的核心。相关特征包括：
- **用户特征**：人口统计信息、浏览历史、购买历史、设备类型、地理位置、时间等。
- **广告特征**：广告内容（图片/文本）、广告主信息、广告类别、历史点击率、出价金额等。
- **上下文特征**：页面内容、广告展示位置、设备类型、网络连接速度等。
- **交叉特征**：用户类别与广告类别的交互关系，用户所在地区与广告活动的交互关系。

- **模型**：传统上使用逻辑回归模型（简单、快速且易于理解）。现代系统则采用深度学习模型——即**DLRM**（深度学习推荐模型），该模型利用嵌入表来处理分类特征，同时用多层感知机来处理连续特征。

- **概率校准**：预测出的概率必须准确无误（如果模型预测的点击率为0.05，那么实际被点击的广告应占5%）。概率校准非常重要，因为预测概率直接决定了出价金额。

- **探索与利用平衡**：始终展示预测为最佳的广告从长远来看并非最佳策略（因为这样就无法发现可能有更好的广告）。Thompson采样或$\epsilon$-贪婪算法可用于让部分展示机会留给那些不确定性较高的广告，从而收集更多数据。

### 实时竞标

- 当用户加载页面时，广告竞标会在100毫秒内完成：

1. 广告发布方将包含用户信息和页面上下文的竞标请求发送给多个广告交易平台。
2. 每个广告主的竞价服务器会预测其广告的点击率。
3. 出价 = 点击率 × 每次点击的价值。出价最高的广告获胜。
4. 获胜的广告会被展示出来；如果用户点击了该广告，广告主就需要支付费用。

## 4. 欺诈检测

### 问题描述（续1）

- **目标**：实时检测欺诈性交易（如信用卡欺诈、账户盗用、虚假评论等）。
- **响应时间要求**：必须在100毫秒内完成检测，以便在支付流程开始之前做出决策。
- **主要挑战**：欺诈行为的比例极低（仅为0.1%）。过多的误报会妨碍合法用户的正常使用，而漏报则会导致经济损失。

### 架构（续1）

![欺诈检测流程：交易数据 → 实时特征提取 → 机器学习模型 → 决策引擎 → 允许/审核/阻止，同时通过人工审核为模型提供标签以用于重新训练](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/fraud_detection_pipeline.svg)

### 特征（续1）

- **交易特征**：交易金额、货币类型、商家类别、交易时间、是否为国际交易等。
- **用户特征**：账户使用时长、平均交易金额、近期交易次数、设备指纹等。
- **频率特征**（来自实时数据流）：过去5分钟内的交易数量、过去1小时内的不同商家数量、与上一次交易之间的地理距离等。
- **图结构特征**：该商家是否与已知的欺诈团伙有关？该设备是否曾被标记为异常的账户使用？

### 模型

- **梯度提升树**（如XGBoost、LightGBM）是用于表格数据欺诈检测的标准模型。这类模型能够处理多种类型的特征，且具有可解释性（可识别出各特征的重要性），同时训练速度也很快。

- **处理类别不平衡问题**：可以通过对多数类进行降采样、对少数类进行过采样（SMOTE方法），或在损失函数中加入类别权重来解决这一问题。Focal损失算法（见第8章）则可以降低容易识别的负样本的权重。

- **成本矩阵**：误报（阻止了合法交易）会带来用户不满和销售损失等成本；而漏报（未能发现欺诈行为）则会导致财务损失。因此，决策阈值应旨在最小化总预期成本，而非最大化准确率。

### 人工干预机制

- 对于那些预测置信度在0.3到0.7之间的不确定结果，会将其提交给人工审核员进行处理。审核员的决策结果会被用作重新训练模型的标签。这样一来，随着模型接触到越来越多的标注过的欺诈案例，其性能也会逐渐提升。

## 5. 内容审核

### 问题描述（续2）

- **目标**：自动检测并删除平台上的有害内容，如仇恨言论、暴力内容、错误信息、儿童色情内容等。
- **处理规模**：每天有数十亿条帖子需要处理，包括文本、图片和视频。
- **挑战**：内容含义往往取决于上下文（比如讽刺、双关语、文化差异等）。因此，需要在保障内容自由表达与维护平台安全之间找到平衡点。

### 架构（续2）

- **多模态分类**：分别为文本、图片和视频建立独立的分类模型，再通过融合层将各模型的输出结果整合起来。

- **文本审核**：经过微调的语言模型可将文本分类为不同类别，如骚扰内容、仇恨言论、错误信息、垃圾信息等。多语言模型则可处理100多种语言的文本。

- **图片审核**：视觉模型可用于检测露骨内容、暴力内容，以及图片中的文字内容（通过OCR技术提取文字后再进行分类）。此外，还可以通过哈希值与已知的有害内容数据库进行比对。

- **视频审核**：定期抽取视频中的帧，对每一帧进行图片分类，同时结合音频转录结果（通过ASR技术将音频转换为文本后再进行分类）来进行综合判断。

- **政策编码化**：审核规则以结构化的形式定义，将模型的输出结果映射到具体的操作指令上。

```python
if text_model.hate_speech_score > 0.9:
    action = "remove"
elif text_model.hate_speech_score > 0.7:
    action = "human_review"
else:
    action = "allow"
```

- 政策会频繁变化（新法规、不断变化的规范）。将政策与模型分开，就可以在无需重新训练的情况下应用这些变化。

### 主动式与被动式内容审核

- **主动式**（发布前）：在内容上线之前就对其进行分析。那些被判定为违规的内容会自动被拦截。这样就能防止有害内容被展示出来，但会导致发布延迟，同时还存在误判的风险（即误拦截合法内容）。

- **被动式**（发布后）：内容会立即被展示出来，用户可以举报违规内容。收到举报后，系统会先通过分类器进行检测，然后再由人工进行审核。这种方式能减少发布延迟，但有害内容仍会在被发现之前一直可见。

- **大多数平台会同时采用两种方式**：对于严重违规的内容（如儿童色情内容），则采用主动式审核——在内容发布前就将其拦截；而对于较为复杂的违规内容（如虚假信息），则采用被动式审核——等待用户举报后再进行人工审核。

### 哈希匹配

- 对于已知的有害内容（如儿童色情内容、恐怖主义宣传内容），可以使用**感知哈希技术**：对图像或视频计算哈希值，这种哈希值能够抵抗一些小的修改操作（如裁剪、调整大小、压缩等）。然后将计算出的哈希值与已知有害内容的数据库进行比对（如NCMEC的哈希数据库、GIFCT共享的哈希数据库）。一旦匹配成功，就可以立即删除该内容，无需再通过分类器进行检测。

- **PhotoDNA**（微软开发）是用于检测儿童色情内容的标准感知哈希技术。在许多地区，使用这种技术不仅是技术上的选择，更是法律上的要求。

### 粗略估算

- **数据量**：如果每天有10亿条帖子，那么相当于每秒有1.2万条帖子被处理。每条帖子需要经过文本分类（约5毫秒）、图像分类（约20毫秒）以及哈希匹配（约1毫秒）的处理。以每秒1.2万条帖子的速度来计算，就需要大约60个文本分类器、240个图像分类器以及12个哈希匹配器——当然，这里还考虑了冗余因素。

- **人工审核**：如果2%的帖子需要人工审核，那么每天就有2000万条帖子需要审核。如果每位审核员每天能处理100条帖子，那么就需要20万名审核员。这就是为什么提高自动系统的准确率如此重要：每降低0.1%的误判率，就能每天节省100万条帖子的审核工作量。

- **延迟限制**：主动式内容审核必须在内容发布流程之内完成，时间上限约为500毫秒。文本分类需要5毫秒，图像分类需要20毫秒，哈希匹配需要1毫秒，再加上其他开销，总时间仍在允许范围内。不过，对于视频内容来说则有所不同：即使是从10分钟长的视频中每秒抽取1帧，也需要进行600次分类器检测——因此这类处理必须以异步方式进行。

### 升级处理流程

- 首先自动删除违规内容，然后对相关申诉进行人工审核，接着由专家（如法律专家、文化专家）进行进一步审核，对于那些难以判断的情况，则交由政策团队处理。每一层处理的案例数量较少，但需要处理更复杂的情况。

- **为模型提供反馈**：人工审核的结果是最优质的训练数据，可用于模型的重新训练。模型与审核结果之间存在分歧时，这些分歧会被优先用于主动学习——因为它们代表了模型最容易出错的场景。

## 6. 对话式人工智能（基于RAG的聊天机器人）

### 问题定义（续3）

- **目标**：打造一种能够利用公司文档来回答有关其产品问题的聊天机器人。
- **要求**：回答必须准确无误（不能出现错误信息），需要注明信息来源，能够处理后续问题，且内容必须与产品相关。

![RAG架构图：将查询嵌入到向量数据库中，搜索出相关的信息片段，再对这些片段进行排序，最后将它们与原始查询一起输入到大语言模型中，从而生成有依据的回复](https://henryndubuaku.github.io/maths-cs-ai-compendium/images/rag_architecture.svg)

### 架构：检索增强生成（RAG）

```text
User query → Query Embedding → Vector Search (documentation) → Top-K chunks
                                                                      ↓
User query + Retrieved chunks → LLM → Response (with citations)
```

### 组件

- **文档处理**：将文档分割成多个片段并对其进行嵌入。**分割策略**至关重要：

- **固定大小分割**：每N个令牌为一个片段，同时设置M个令牌的重叠部分（例如，N=500，M=50）。这种方式简单且易于预测，但可能会导致句子或段落被截断，从而丢失上下文信息。

- **语义分割**：在段落或章节边界处进行分割。每个片段都是一个完整的信息单元。片段大小不一（有的为100个令牌，有的为800个令牌），因此检索系统需要能够处理不同长度的片段。

- **递归分割**：首先尝试在段落边界处进行分割；如果某个段落过长，则在句子边界处分割；如果句子仍过长，则按固定大小进行分割。这种方式能在保持内容连贯性的同时确保片段大小的一致性。

- **嵌入处理**：使用文本编码器（如E5、BGE、Cohere Embed）对每个片段进行嵌入，然后将这些嵌入向量存储在向量数据库中。

- **检索阶段**：对用户查询进行嵌入处理，然后在向量数据库中查找与查询最相似的$k$个片段（通常$k=5$–$10$）。如有需要，还可以通过交叉编码器对结果进行重新排序，以提高精确度。

- **生成阶段**：以检索到的片段作为上下文，构建相应的提示语。

```text
System: You are a helpful assistant. Answer based ONLY on the provided context.
If the answer is not in the context, say "I don't know."

Context:
[chunk 1]
[chunk 2]
...

User: {question}
```

- **约束机制**：防止大型语言模型回答超出产品范畴的问题、生成有害内容，或与已获取的上下文相矛盾。实现方式包括：输入过滤（拒绝与主题无关的查询）、输出过滤（将响应与已获取的上下文进行比对），以及原则性提示（指示模型拒绝某些请求）。

- **对话记忆**：保存最近$n$轮对话内容。将这些内容纳入提示语中，以便模型理解后续问题（例如“价格是多少？”——需要之前关于该产品的上下文信息）。

### 查询重写

- 用户常常会提出含义模糊的后续问题，比如“价格是多少？”（到底什么的价格？）。**查询重写**功能会利用对话历史来生成一个结构清晰的独立查询：

- 输入：对话历史 + “价格是多少？”
- 重写后的查询：“产品X的企业版价格是多少？”

- 这个经过重写的查询会被嵌入到向量数据库中进行搜索。如果不进行重写，数据库会在没有上下文的情况下搜索“价格”这个词，从而返回无关的信息。

- 查询重写可以通过调用小型大型语言模型来完成（耗时约50毫秒），或者使用经过微调的序列到序列模型来实现（耗时约5毫秒）。

### 大致估算数据

- **文档语料库**：1万页，每页平均2000个令牌，总计2000万令牌。若每个片段包含500个令牌且存在50%的重复度，则共有约4.4万个片段。
- **嵌入索引**：4.4万个片段 × 768维 × float16格式 = 约65MB，完全可以存储在内存中。即便有1000万个片段，其存储容量也仅为约15GB。
- **延迟分析**：查询嵌入耗时5毫秒，向量搜索耗时2毫秒，交叉编码器重新排序耗时20毫秒（用于筛选出前50个结果），大型语言模型生成文本的耗时为500至2000毫秒，总延迟约为600至2100毫秒。其中大型语言模型的处理时间占主导地位。通过流式处理可以降低感知到的延迟。
- **成本计算**：按照每100万令牌3美元的API费用标准，如果每天有1000次查询，每次查询对应的令牌数约为2000个，那么每日成本约为6美元。如果查询量达到每天100万次，可以在2块A10G显卡上部署70亿参数的模型，这样每日成本约为50美元，可节省100倍的开支。

### 评估指标

- **检索质量**：Recall@K（前K个片段中是否包含正确答案？）、MRR（平均互反排名）。
- **生成质量**：事实准确性（响应内容是否与已获取的上下文一致？）、依据性（响应是否引用了正确的片段？）、答案的相关性。
- **端到端评估**：用户满意度（点赞/点踩）、需要人工干预的比例。

## 7. 大规模图像搜索

### 问题描述（续3）

- **目标**：给定一张图片，从包含10亿多张图片的数据库中找到视觉上相似的图片。
- **应用场景**：反向图像搜索、产品搜索（通过图片查找对应产品）、重复图片检测。
- **延迟要求**：包括网络往返时间在内，延迟需低于500毫秒。

### 架构设计

```text
Query image → Embedding Model (ViT/CLIP) → 512-dim vector → ANN Search → Top-K results
```

### 嵌入向量提取

- **模型**：预训练的视觉编码器（ViT、CLIP的图像编码器、DINOv2）。如需针对特定领域（时尚、电子商务、医学影像等）进行优化，可对该模型进行微调。

- **训练方式**：对比学习（见第10章）。正样本对为同一图像的不同视角（或图像与对应的文本）；负样本对为随机图像。模型会学会为相似的图像生成相似的嵌入向量，而为不同的图像生成不同的嵌入向量。

### 索引构建

- **离线处理**：将所有10亿张图像的嵌入向量存储起来，从而构建出ANN索引。对于HNSW算法（见文件03），构建索引需要数小时时间，而索引本身则存储在内存中——10亿张图像、每张图像512维、采用float16格式时，加上图表结构所需的空间，大约需要128GB的内存。

- **分片处理**：将索引拆分到多台机器上，每台机器负责存储一部分索引。查询时，可同时搜索所有分片中的数据，然后合并出Top-K的结果。

- **增量更新**：新上传的图像需要被添加到索引中。HNSW算法支持无需重新构建索引即可实现增量插入。向量数据库（如Milvus、Pinecone）则具备这种内置功能。

### 服务提供

- **嵌入向量服务**：由运行ViT模型的GPU服务器提供。每张图像的查询延迟约为20毫秒。为了提高处理效率，可以批量处理多个查询。

- **搜索服务**：由ANN索引服务器提供。使用HNSW算法时，对10亿个向量进行前100个结果的查询，其延迟约为10毫秒。

- **缓存机制**：对频繁被查询的结果进行缓存。在检测重复图像时，可以先缓存最近上传的图像的嵌入向量，再在新图像被查询时先与缓存中的向量进行比对，之后才去查询完整的索引。

### 评估方法（续1）

- **Precision@K**：Top-K结果是否确实具有相似性？
- **Recall@K**：在所有真正相似的图像中，有多少被包含在Top-K结果中？
- **平均精度均值（mAP）**：精度-召回曲线下的面积。
- **人工评估**：对于主观上的相似性判断，由人类评估员来判定检索到的图像是否相关。

## 面试框架

- 当遇到系统设计类问题时，可遵循以下框架：

1. **明确需求**（2-3分钟）：了解系统的规模、延迟要求、一致性要求以及各种边界情况。“有多少用户？可接受的延迟是多少？出现故障时该如何处理？”

1. **整体设计**（5-7分钟）：绘制出系统的主要组成部分及其相互关系。先从正常情况下的系统流程入手，参考文件01-03中的设计思路。

1. **深入设计**（15-20分钟）：选择最复杂或最具挑战性的部分，对其进行详细设计。这部分内容能体现你的专业深度。对于机器学习系统而言，通常需要深入设计的方面包括模型架构、特征处理流程或服务架构。

1. **评估与监控**（3-5分钟）：如何衡量系统的成功与否？可能出现哪些问题？如何检测并解决这些问题？

1. **迭代改进**（2-3分钟）：如果有更多时间和资源，你会对系统做哪些改进？这能体现你理解各种权衡关系，并能够合理分配优先级。

- **面试官看重的要点**：结构化的思维方式（不会急于给出解决方案）、对权衡关系的理解（每个决策都有相应的成本）、实际开发经验（真正有过系统构建经验），以及沟通能力（能否清晰地阐述自己的设计思路）。
